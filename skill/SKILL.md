# /kickstart

ผู้ใช้ไม่ต้องคัดลอกพรอมต์จาก `02-prompts.md` อีก สกิลนี้อ่านสถานะของ repo แล้วทำขั้นถัดไปให้
ถ้าขั้นนั้นต้องใช้สกิลที่ผู้ใช้ต้องพิมพ์เอง ให้จบเทิร์นด้วยกล่องบอกคำสั่งที่ต้องพิมพ์

## แหล่งข้อมูล

KIT คือโฟลเดอร์ที่ clone ชุดนี้ไว้ สกิลนี้เป็นลิงก์ไปที่ `KIT/skill` ให้หา path จริงก่อนอ่านไฟล์แรก:
`node -e "console.log(require('fs').realpathSync(process.argv[1]))" "<โฟลเดอร์ของสกิลนี้>"` แล้ว KIT คือโฟลเดอร์แม่ของผลลัพธ์
ยืนยันว่ามี `KIT/01-playbook.md` ถ้าไม่เจอ (เช่น ติดตั้งด้วยการคัดลอก) ให้ถามผู้ใช้ว่า clone ชุดไว้ที่ไหน
`KIT/...` ในพรอมต์ทุกตัวให้แทนด้วย path นี้ อ่านเฉพาะส่วนของขั้นที่กำลังทำ ไม่ต้องอ่านทั้งไฟล์

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `KIT/01-playbook.md` หัวข้อ "ขั้นที่ N" | เป้าหมาย เกณฑ์ "เสร็จ" และกับดักของขั้น |
| `KIT/02-prompts.md` หัวข้อ "PN" | คำสั่งของขั้น ให้ทำตามเหมือนผู้ใช้ส่งมาเอง ("ผม" ในพรอมต์คือผู้ใช้) และแทน `<...>` ด้วยข้อมูลจริงจาก repo |
| `KIT/03-project-shapes.md` | แถวของรูปแบบโปรเจกต์นี้ |
| `KIT/04-owner-preferences.md` | หลักที่ใช้ทุกโปรเจกต์ ทำตามได้เลย (ไม่มีการเลือก stack อยู่ในนั้น ต้องเสนอตัวเลือกตามโจทย์ทุกครั้ง) |
| `KIT/templates/` | ไฟล์แม่แบบของขั้นที่ 1 และของที่ใช้ซ่อมโปรเจกต์เก่า |

สถานะของโปรเจกต์อยู่ที่ `docs/progress.md` ใน repo (รูปแบบอยู่ท้ายไฟล์นี้)

## โหมด

| ผู้ใช้พิมพ์ | ทำอะไร |
|---|---|
| `/kickstart` | หาขั้นปัจจุบัน แล้วทำต่อหรือบอกคำสั่งถัดไป |
| `/kickstart status` | แสดงตารางสถานะจาก `docs/progress.md` และขั้นถัดไป ไม่ทำงานใดๆ |
| `/kickstart feature <ชื่อ>` | เริ่มวงฟีเจอร์ใหม่ที่ขั้น 4 (ต้องผ่านขั้น 3 แล้ว) หลังผ่าน "ด่านก่อนเริ่มฟีเจอร์ใหม่" ด้านล่าง |
| `/kickstart step <N>` | ข้ามไปขั้น N ตามที่ผู้ใช้สั่ง บันทึกใน progress ว่าข้ามขั้นไหน |
| `/kickstart health` | ทำ "ตรวจสุขภาพ repo" ใน P9 แล้วรายงาน ไม่แก้อะไร |
| `/kickstart adopt` | นำชุดไปใช้กับโปรเจกต์ที่มีโค้ดอยู่แล้ว ตามหัวข้อ "โหมด adopt" ด้านล่าง |

ถ้าพิมพ์ `/kickstart` เฉยๆ ใน repo ที่มีโค้ดแอปอยู่แล้วแต่ไม่มี `docs/progress.md` และไม่มี `docs/brief.md` ให้ถามว่าเป็นโปรเจกต์ที่มีอยู่แล้วหรือไม่ ถ้าใช่ ให้ไปโหมด adopt

## โหมด adopt (โปรเจกต์ที่มีอยู่แล้ว)

ใช้ repo เดิม ไม่สร้าง repo ใหม่ อ่านหัวข้อ "นำไปใช้กับโปรเจกต์ที่มีอยู่แล้ว" ใน `KIT/01-playbook.md` และ PA1–PA4 ใน `KIT/02-prompts.md`

| ขั้น | ทำอะไร | จุดที่ต้องรอผู้ใช้ |
|---|---|---|
| A1 | PA1 สำรวจแบบอ่านอย่างเดียว รันได้เฉพาะคำสั่งที่ไม่แก้สถานะ | ผู้ใช้อนุมัติแผน PA2–PA4 |
| A2 | สร้าง branch ใหม่ (ถามชื่อถ้าคลังมีธรรมเนียมตั้งชื่อ branch) แล้วทำ PA2 | ผู้ใช้แก้ brief · `/setup-matt-pocock-skills` ให้ผู้ใช้พิมพ์ตอนไหนก็ได้ก่อนขั้น 4 (ต้องอยู่ใน session ที่เปิดใน repo นั้น) ไม่ต้องหยุดรอ |
| A3 | PA3 (เรียกสกิล `domain-modeling` ช่วยเขียน ADR และ glossary ได้) | ผู้ใช้เลือกจากรายการ "ควรตัดสิน" |
| A4 | PA4 แล้วสร้าง `docs/progress.md` (ขั้น 0–3 "นำเข้าแล้ว" · ขั้นถัดไป 4) | ผู้ใช้อนุมัติ merge branch นำเข้า ห้าม merge หรือ push เอง |

**"ขั้นตอนทุกครั้ง" ใช้ต่างไปในโหมดนี้**
- A1: ข้ามข้อ 1 (ยังไม่มี `.claude/` เป็นเรื่องปกติ) ข้อ 2 ห้ามสร้าง progress.md ข้อ 3 ห้ามซ่อม และข้อ 5–6 ห้าม commit · A1 อ่านอย่างเดียวทั้งหมด
- A2–A3: ข้ามข้อ 3 (การซ่อมคือ PA2 อยู่แล้ว) · progress.md สร้างใน A4 เท่านั้น ระหว่างนั้นให้บอกสถานะในกล่องขั้นถัดไป
- หลัง A4: กลับไปใช้ "ขั้นตอนทุกครั้ง" ตามปกติ

**อนุมานกับ repo ที่มีอยู่แล้ว**
- บรรทัดสถานะของ ADR ใช้รูปแบบเดิมของ repo ได้ (เช่น `**สถานะ:** ตัดสินแล้ว`) ไม่ต้องเป็น `Status:`
- การตัดสินใจที่เขียนไว้ในเอกสารอื่น (เช่น PLAN, README) แล้วมี ADR สั้นที่ชี้ไป ถือว่ามี ADR
- เอกสารเดิมที่ทำหน้าที่ brief หรือ progress อยู่แล้ว ให้ `docs/brief.md` ชี้ไปที่นั้น ไม่เขียนซ้ำ

กติกาเพิ่มของโหมดนี้
- ห้ามแก้โค้ดของแอปตลอด A1–A4 (ยกเว้น error ชั่วคราวที่ใส่เพื่อพิสูจน์ด่านแล้วลบออก) การจัดโครงใหม่เป็นงานแยกหลังนำเข้าเสร็จ
- ไฟล์ที่มีอยู่แล้วต้องรวม ห้ามเขียนทับ ถ้ากฎขัดกันให้ถาม
- `CODING_STANDARDS.md` ห้ามมีข้อที่โค้ดเดิมขัดทั้งระบบ เว้นแต่ติดป้าย "(โค้ดใหม่)"
- `CHECKS` ใส่เฉพาะเช็กที่เขียวบน branch หลักแล้ว
- progress.md ของโหมดนี้: บรรทัดหัวใช้ `ขนาดงาน: นำเข้า` · ขั้น 0–3 ติ๊กเป็น `[x] … (นำเข้า YYYY-MM-DD)` · ตาราง "ฟีเจอร์" เริ่มว่าง
  งานที่เสร็จก่อนนำเข้าไม่ต้องลง ให้เขียนบรรทัด `งานก่อนนำเข้า: ดู <เอกสารเดิม หรือ git log>` · ขั้นที่ข้าม (2.5 และการสร้างโครงของขั้น 3)
  บันทึกในหัวข้อ "ข้ามหรือเปลี่ยนจากแผน" พร้อมเหตุผลว่าเป็นโปรเจกต์ที่มีอยู่แล้ว
- ถ้าเอกสารเดิมมีตารางความคืบหน้าของตัวเอง ให้ถามผู้ใช้ว่าจะใช้ progress.md แทน หรือเก็บไว้ทั้งคู่ (ห้ามปล่อยให้สองที่ขัดกันเงียบๆ)
- รายการ "ควรตัดสิน" จาก A3 ลงใน progress.md เป็นหัวข้อ `## ควรตัดสิน (จากการนำเข้า)` ก่อนหัวข้อ "ข้ามหรือเปลี่ยนจากแผน" แต่ละข้ออ้าง ADR หรือรหัสมาตรฐานที่เกี่ยวข้อง ข้อที่ผู้ใช้ตัดสินแล้วให้ลบออก (ผลไปอยู่ใน ADR หรือ commit)
- ระหว่าง A4 ด่านตรวจยังไม่ทำงานใน session นี้จนกว่า session จะเปิดใหม่ใน repo (hooks โหลดตอนเปิด session) ให้พิสูจน์ด่านด้วยการรัน `verify.mjs` เองตาม PA4

## ขั้นตอนทุกครั้ง

1. **ตรวจที่อยู่ของ session** ถ้า session ไม่ได้เปิดในโฟลเดอร์โปรเจกต์ (ไม่มี `.claude/` ของโปรเจกต์ หรือ cwd เป็นโฟลเดอร์แม่) ให้เตือนว่า hooks จะไม่ทำงาน
   ยกเว้นขั้นที่ 0 ที่ยังไม่มี repo
2. **หาขั้นปัจจุบัน** อ่าน `docs/progress.md` ก่อน ถ้าไม่มี ให้อนุมานจากไฟล์ตามตารางด้านล่าง
   แล้วสร้าง progress.md จากสิ่งที่พบ ข้อที่ไม่แน่ใจ (เช่น ticket ไหนเสร็จแล้ว) ให้เขียนว่า "คาดว่า" แล้วถามผู้ใช้ยืนยันก่อนทำต่อ
3. **ซ่อมโปรเจกต์ที่ตั้งก่อนชุดรุ่นปัจจุบัน** (ทำครั้งเดียว บอกผู้ใช้ว่าเพิ่มอะไร แล้ว commit แยก)
   - `CLAUDE.md` ไม่มีหัวข้อ "ลำดับงาน" หรือ "เตรียม worktree" → คัดลอกจาก `KIT/templates/CLAUDE.md` แล้วเติมค่าจริงของโปรเจกต์
   - `.claude/settings.json` ไม่มี hook `SubagentStop` หรือ `verify.mjs` ไม่มีโหมด `subagent-stop` → agent ใน worktree ไม่ผ่านด่าน
     ให้คัดลอกส่วนท้ายของ `KIT/templates/.claude/hooks/verify.mjs` (ตั้งแต่ `const OUTPUT_TAIL_LINES` ลงไป) และ hook จากแม่แบบ settings โดยคง `CHECKS`/`FORMATTERS` ของโปรเจกต์ไว้
   - ไม่มี `.worktreeinclude` แต่มี `.env` ที่ git ignore → สร้างจากแม่แบบ
   - Edit/Write ใน auto mode ช้าครั้งละหลายวินาที (ดู `permissionDecision` ของ Edit ใน transcript ถ้าเป็น `classifier`) และ `~/.claude/settings.json` ไม่มีกฎ `Edit(//...)` ครอบโฟลเดอร์ของโปรเจกต์ → เสนอตั้งกฎระดับผู้ใช้ตามขั้น 1 ข้อ 4 ของ playbook (ถามโฟลเดอร์ บอกข้อแลก รอคำตอบตกลง ถ้าระบบไม่ให้แก้ให้บอกบรรทัดที่ต้องเพิ่ม) · `Edit(/**)` ใน `.claude/settings.json` ของโปรเจกต์ไม่ต้องเพิ่ม (ใช้ได้เฉพาะเมื่อโฟลเดอร์ trust แล้ว)
   - หัวข้อ "เตรียม worktree" ไม่มีข้อห้ามใช้คำสั่งในรายการ `ask` หรือข้อห้ามสร้างข้อมูลทดสอบใน DB ของ dev → เพิ่มจากแม่แบบ
   - `FORMATTERS` ตัวที่เรียกของใน `node_modules` หรือ venv แต่ไม่มี `needs` → เพิ่ม `needs` (ไม่งั้น hook ล้มทุกครั้งที่ agent แก้ไฟล์ใน worktree ที่ยังไม่ได้ติดตั้ง)
   - `verify.mjs` ไม่มี `CLAUDE_MD_LIMIT` → คัดลอกส่วนท้ายแบบเดียวกับข้อบน · CLAUDE.md ไม่มีตาราง "ก่อนแตะเรื่องไหน อ่านอะไร" → เพิ่มจากแม่แบบ ถ้าเกินเพดานให้ทำตาม "ย้ายรายละเอียดออกจาก CLAUDE.md" ใน P9
   - `verify.mjs` ไม่มี `PROGRESS_LIMIT` (หรือ `LENGTH_LIMITED_DOCS`) → คัดลอกส่วนท้ายแบบเดียวกับข้อบน · `docs/progress.md` เกิน 8,000 ตัวอักษร → ทำตามพรอมต์ "ย้ายประวัติออกจาก docs/progress.md" ใน P9 (ตัดมาทั้งก้อนไป `.scratch/<ฟีเจอร์>/log.md` ห้ามสรุปใหม่ พิสูจน์ด้วยโทเคนใน backtick)
   - ต้องยกระบบเพื่อดูผล (เว็บ API worker mobile desktop) แต่ไม่มี `.claude/skills/run-*/` หรือ CLAUDE.md ไม่มีบรรทัด "การตรวจบนระบบจริง" → ทำตาม **P3c** (สคริปต์ยกระบบที่คัดลอกต่อใบงานใน `.scratch/` รวมเข้าสกิลนั้น)
   - **`.claude/settings.json` ห้ามเขียนเอง** auto mode ปฏิเสธการแก้ไฟล์สิทธิ์ของตัวเองทุกครั้ง (Self-Modification) และห้ามหาทางอ้อม
     ให้เขียนไฟล์ที่รวมแล้ว (ของเดิมทั้งหมด + ส่วนที่ขาดจากแม่แบบ) ไว้ที่ `.scratch/settings.proposed.json` แล้วบอกผู้ใช้ว่าเพิ่มอะไร
     พร้อมคำสั่งเดียวให้รันเอง: `mv .scratch/settings.proposed.json .claude/settings.json` ห้าม commit ไฟล์ proposed
     หลังผู้ใช้ย้ายแล้ว ตรวจว่าเป็น JSON ที่ถูกต้องแล้ว commit `.claude/settings.json` · hook ใหม่ทำงานเมื่อเปิด session ใหม่
     ซ่อมข้ออื่นต่อได้โดยไม่ต้องรอ
4. **เทียบ progress กับ repo จริง** ถ้าไม่ตรงกัน (เช่น progress บอกขั้น 5 แต่มี issues ครบแล้ว) ให้เชื่อ repo แล้วแก้ progress
5. **ทำขั้นนั้น** ตามตาราง "ใครทำ" ด้านล่าง จบขั้นแล้ว commit เองโดยไม่ต้องถาม (ห้าม push)
6. **อัปเดต `docs/progress.md`** ทั้งเครื่องหมายขั้นและหัวข้อ "ขั้นถัดไป" แล้ว commit ไปพร้อมงานของขั้น · ฟีเจอร์ที่ merge แล้วเหลือแถวเดียว (ชื่อ · commit ที่ merge · ลิงก์ `.scratch/<ฟีเจอร์>/`) ประวัติและเรื่องที่ตัดสินแล้วย้ายไป `.scratch/<ฟีเจอร์>/log.md` ไฟล์นี้มีเพดาน 8,000 ตัวอักษรที่ `verify.mjs` วัด
7. **จบเทิร์นด้วยกล่องขั้นถัดไป** (รูปแบบด้านล่าง) เสมอ

### สถานะ ticket

ใบหนึ่งถือว่าเสร็จเมื่อข้อใดข้อหนึ่งจริง
1. บรรทัด `Status:` เป็นคำที่แปลว่าเสร็จตาม `docs/agents/issue-tracker.md` (หรือ `triage-labels.md` ถ้ามี) ถ้าไม่ได้กำหนด ใช้ `done`
2. `git log --all --grep "Ticket: <feature>/<NN>"` เจอ commit ที่อยู่ใน branch ของฟีเจอร์แล้ว

ถ้าไม่มีทั้งสองอย่าง (โปรเจกต์เก่า) ให้เทียบเกณฑ์ของ ticket กับ commit ของทุก branch (`git log --all`) แล้วเขียน "คาดว่า" ให้ผู้ใช้ยืนยัน
**ใบถัดไป** คือใบแรกที่ยังไม่เสร็จ ทุกใบใน blocked by เสร็จแล้ว และไม่มี worktree ที่กำลังทำใบนั้นอยู่

### worktree

ตรวจ `git worktree list --porcelain` และโฟลเดอร์ใน `.claude/worktrees/` แล้วแยกเป็น
- **locked** → อาจมี agent หรือ session อื่นทำงานอยู่ ห้ามแนะนำใบที่ worktree นั้นทำ ห้ามลบ
- **มี `MERGE_HEAD` หรืองานที่ยังไม่ commit** → งานค้าง บอกผู้ใช้ ห้ามลบเอง
- **สะอาดและ HEAD อยู่ใน branch ของฟีเจอร์แล้ว** → ลบได้ เสนอให้ผู้ใช้ตอนขั้น 7
- **โฟลเดอร์ที่ git ไม่รู้จัก** → ของกำพร้า เสนอให้ผู้ใช้ลบ

### ด่านก่อนเริ่มฟีเจอร์ใหม่

ทำทุกครั้งที่จะเข้าขั้น 4 เมื่อมีเรื่องค้างหรือมีฟีเจอร์ที่ merge แล้ว (ฟีเจอร์แรกของโปรเจกต์ใหม่ไม่มีอะไรให้ถาม) ผู้ใช้ต้องตอบทั้งสองข้อก่อน ห้ามเริ่มขั้น 4 ระหว่างรอ

1. **เรื่องรอตัดสินที่ค้าง** รวบรวมจากหัวข้อ "รอตัดสิน" และ "ควรตัดสิน (จากการนำเข้า)" ใน progress.md ใบงานที่ค้างเพราะรอคำตอบจากผู้ใช้ (ดูช่อง ticket และหมายเหตุของตารางฟีเจอร์) และข้อที่ผลเป็น "ผมตัดสิน" แต่ยังไม่มีคำตอบใน `.scratch/*/review.md` กับ `security-review.md`
   เขียนเป็นการ์ดที่ `.scratch/decisions/pending.md` (รหัส · เรื่อง · ค้างตั้งแต่ฟีเจอร์ไหน · คำแนะนำ · ผลถ้าไม่ทำ) แล้ว **ถามทีละข้อ ห้ามมีตัวเลือกตอบรวมทั้งชุด**
   คำตอบมีสามแบบ: ทำ (เปิดเป็นใบงานหรือใส่ในฟีเจอร์ที่ระบุ) · เลื่อนพร้อมวันที่ · ปิดโดยไม่ทำพร้อมเหตุผล ข้อที่ตอบแล้วย้ายออกจาก progress.md
   ข้อที่ตัดสินว่า "ทำ" แต่ยังไม่มีใบงาน ให้คงไว้ในหัวข้อ "รอตัดสิน" พร้อมคำว่า "รอเปิดใบ"
2. **รอบทบทวนโครงสร้าง** นับแถวฟีเจอร์ที่วันที่ merge อยู่หลังวันที่ในบรรทัด "ทบทวนโครงสร้างล่าสุด" ของ progress.md (ถ้า "ยังไม่เคย" นับทุกแถวที่ merge แล้ว · แถวที่ไม่มีวันที่ให้ดูจาก `git log` ของ commit ที่ merge) ถ้าครบ 3 ให้ถามว่าจะรัน `/improve-codebase-architecture` ก่อนหรือข้าม
   ถ้ารัน: เขียนรายการหนี้ที่รีวิวเลื่อนไว้ลง "ขั้นถัดไป" แล้วให้ผู้ใช้พิมพ์ `/improve-codebase-architecture ทำตาม "ขั้นถัดไป" ใน docs/progress.md` ใน session ใหม่ จบแล้วแก้วันที่ในบรรทัดนั้น
   ถ้าข้าม: จดเหตุผลใน "ข้ามหรือเปลี่ยนจากแผน" และถามใหม่ที่ฟีเจอร์ถัดไป
