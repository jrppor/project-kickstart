# /kickstart

ผู้ใช้ไม่ต้องคัดลอกพรอมต์จาก `02-prompts.md` อีก สกิลนี้อ่านสถานะของ repo แล้วทำขั้นถัดไปให้
ถ้าขั้นนั้นต้องใช้สกิลที่ผู้ใช้ต้องพิมพ์เอง ให้จบเทิร์นด้วยกล่องบอกคำสั่งที่ต้องพิมพ์

## แหล่งข้อมูล

KIT คือโฟลเดอร์ที่ clone ชุดนี้ไว้ สกิลนี้เป็นลิงก์ไปที่ `KIT/skill` ให้หา path จริงก่อนอ่านไฟล์แรก:
`node -e "console.log(require('fs').realpathSync(process.argv[1]))" "<โฟลเดอร์ของสกิลนี้>"` แล้ว KIT คือโฟลเดอร์แม่ของผลลัพธ์
ยืนยันว่ามี `KIT/01-playbook.md` ถ้าไม่เจอ (เช่น ติดตั้งด้วยการคัดลอก) ให้ถามผู้ใช้ว่า clone ชุดไว้ที่ไหน
`KIT/...` ในพรอมต์ทุกตัวให้แทนด้วย path นี้ อ่านเฉพาะส่วนของขั้นที่กำลังทำ ไม่ต้องอ่านทั้งไฟล์

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `KIT/01-playbook.md` หัวข้อ "ขั้นที่ N" | เป้าหมาย เกณฑ์ "เสร็จ" และกับดักของขั้น |
| `KIT/02-prompts.md` หัวข้อ "PN" | คำสั่งของขั้น ให้ทำตามเหมือนผู้ใช้ส่งมาเอง ("ผม" ในพรอมต์คือผู้ใช้) และแทน `<...>` ด้วยข้อมูลจริงจาก repo |
| `KIT/03-project-shapes.md` | แถวของรูปแบบโปรเจกต์นี้ |
| `KIT/04-owner-preferences.md` | หลักที่ใช้ทุกโปรเจกต์ ทำตามได้เลย (ไม่มีการเลือก stack อยู่ในนั้น ต้องเสนอตัวเลือกตามโจทย์ทุกครั้ง) |
| `KIT/templates/` | ไฟล์แม่แบบของขั้นที่ 1 และของที่ใช้ซ่อมโปรเจกต์เก่า |

สถานะของโปรเจกต์อยู่ที่ `docs/progress.md` ใน repo (รูปแบบอยู่ใน `progress-format.md` ในโฟลเดอร์ของสกิลนี้)

ไฟล์ในโฟลเดอร์ของสกิลนี้ที่อ่านเมื่อถึงเวลาใช้เท่านั้น: `adopt.md` (โหมด adopt) · `repair.md` (ซ่อมโปรเจกต์รุ่นเก่า) · `feature-gate.md` (ก่อนเข้าขั้น 4) · `progress-format.md` (สร้างหรือจัดรูป progress.md และอนุมานขั้นเมื่อไม่มีไฟล์)

## โหมด

| ผู้ใช้พิมพ์ | ทำอะไร |
|---|---|
| `/kickstart` | หาขั้นปัจจุบัน แล้วทำต่อหรือบอกคำสั่งถัดไป |
| `/kickstart status` | แสดงตารางสถานะจาก `docs/progress.md` และขั้นถัดไป ไม่ทำงานใดๆ |
| `/kickstart feature <ชื่อ>` | เริ่มวงฟีเจอร์ใหม่ที่ขั้น 4 (ต้องผ่านขั้น 3 แล้ว) หลังผ่าน "ด่านก่อนเริ่มฟีเจอร์ใหม่" (`feature-gate.md`) |
| `/kickstart step <N>` | ข้ามไปขั้น N ตามที่ผู้ใช้สั่ง บันทึกใน progress ว่าข้ามขั้นไหน |
| `/kickstart health` | ทำ "ตรวจสุขภาพ repo" ใน P9 แล้วรายงาน ไม่แก้อะไร |
| `/kickstart adopt` | นำชุดไปใช้กับโปรเจกต์ที่มีโค้ดอยู่แล้ว ตาม `adopt.md` |

ถ้าพิมพ์ `/kickstart` เฉยๆ ใน repo ที่มีโค้ดแอปอยู่แล้วแต่ไม่มี `docs/progress.md` และไม่มี `docs/brief.md` ให้ถามว่าเป็นโปรเจกต์ที่มีอยู่แล้วหรือไม่ ถ้าใช่ ให้ไปโหมด adopt

## โหมด adopt (โปรเจกต์ที่มีอยู่แล้ว)

ใช้ repo เดิม ไม่สร้าง repo ใหม่ อ่าน `adopt.md` ในโฟลเดอร์ของสกิลนี้ก่อนทำอะไร (ขั้น A1–A4 จุดที่ต้องรอผู้ใช้ และกติกาเพิ่มของโหมดนี้อยู่ที่นั่น)

## ขั้นตอนทุกครั้ง

1. **ตรวจที่อยู่ของ session** ถ้า session ไม่ได้เปิดในโฟลเดอร์โปรเจกต์ (ไม่มี `.claude/` ของโปรเจกต์ หรือ cwd เป็นโฟลเดอร์แม่) ให้เตือนว่า hooks จะไม่ทำงาน
   ยกเว้นขั้นที่ 0 ที่ยังไม่มี repo
2. **หาขั้นปัจจุบัน** อ่าน `docs/progress.md` ก่อน ถ้าไม่มี ให้รัน `node "<โฟลเดอร์ของสกิลนี้>/check-skills.mjs"` จากโฟลเดอร์โปรเจกต์ก่อน
   ถ้าพิมพ์อะไรออกมา ให้ยกข้อความนั้นให้ผู้ใช้ตรงตัวไว้ต้นคำตอบแล้วทำต่อ ไม่ต้องรอ (สกิลที่ผู้ใช้ต้องพิมพ์เองไม่อยู่ในรายการสกิลที่คุณเห็น ห้ามตัดสินจากรายการนั้น)
   จากนั้นอ่าน `progress-format.md` แล้วอนุมานจากไฟล์ตามตารางในนั้น
   แล้วสร้าง progress.md ตามรูปแบบในไฟล์เดียวกัน ข้อที่ไม่แน่ใจ (เช่น ticket ไหนเสร็จแล้ว) ให้เขียนว่า "คาดว่า" แล้วถามผู้ใช้ยืนยันก่อนทำต่อ
3. **ซ่อมโปรเจกต์ที่ตั้งก่อนชุดรุ่นปัจจุบัน** รุ่นรายการซ่อมปัจจุบันคือ 6 ถ้าบรรทัดหัวของ progress.md มี `รุ่นซ่อม: 6` ให้ข้ามข้อนี้
   ถ้าไม่มีหรือเลขน้อยกว่า ให้อ่าน `repair.md` ในโฟลเดอร์ของสกิลนี้แล้วทำตาม (โปรเจกต์ที่เพิ่งตั้งด้วย P1 ของชุดรุ่นนี้ ให้เขียนเลขรุ่นได้เลยโดยไม่ต้องตรวจ)
4. **เทียบ progress กับ repo จริง** ถ้าไม่ตรงกัน (เช่น progress บอกขั้น 5 แต่มี issues ครบแล้ว) ให้เชื่อ repo แล้วแก้ progress
5. **ทำขั้นนั้น** ตามตาราง "ใครทำ" ด้านล่าง จบขั้นแล้ว commit เองโดยไม่ต้องถาม (ห้าม push)
6. **อัปเดต `docs/progress.md`** ทั้งเครื่องหมายขั้นและหัวข้อ "ขั้นถัดไป" แล้ว commit ไปพร้อมงานของขั้น · ฟีเจอร์ที่ merge แล้วเหลือแถวเดียว (ชื่อ · commit ที่ merge · วันที่ merge · ลิงก์ `.scratch/<ฟีเจอร์>/`) ประวัติและเรื่องที่ตัดสินแล้วย้ายไป `.scratch/<ฟีเจอร์>/log.md` ไฟล์นี้มีเพดาน 8,000 ตัวอักษรที่ `verify.mjs` วัด
7. **จบเทิร์นด้วยกล่องขั้นถัดไป** (รูปแบบด้านล่าง) เสมอ


### สถานะ ticket

ใบหนึ่งถือว่าเสร็จเมื่อข้อใดข้อหนึ่งจริง
1. บรรทัด `Status:` เป็นคำที่แปลว่าเสร็จตาม `docs/agents/issue-tracker.md` (หรือ `triage-labels.md` ถ้ามี) ถ้าไม่ได้กำหนด ใช้ `done`
2. `git log --all --grep "Ticket: <feature>/<NN>"` เจอ commit ที่อยู่ใน branch ของฟีเจอร์แล้ว

ถ้าไม่มีทั้งสองอย่าง (โปรเจกต์เก่า) ให้เทียบเกณฑ์ของ ticket กับ commit ของทุก branch (`git log --all`) แล้วเขียน "คาดว่า" ให้ผู้ใช้ยืนยัน
**ใบถัดไป** คือใบแรกที่ยังไม่เสร็จ ทุกใบใน blocked by เสร็จแล้ว และไม่มี worktree ที่กำลังทำใบนั้นอยู่

### worktree

ตรวจ `git worktree list --porcelain` และโฟลเดอร์ใน `.claude/worktrees/` แล้วแยกเป็น
- **locked** → อาจมี agent หรือ session อื่นทำงานอยู่ ห้ามแนะนำใบที่ worktree นั้นทำ ห้ามลบ
- **มี `MERGE_HEAD` หรืองานที่ยังไม่ commit** → งานค้าง บอกผู้ใช้ ห้ามลบเอง
- **สะอาดและ HEAD อยู่ใน branch ของฟีเจอร์แล้ว** → ลบได้ เสนอให้ผู้ใช้ตอนขั้น 7
- **โฟลเดอร์ที่ git ไม่รู้จัก** → ของกำพร้า เสนอให้ผู้ใช้ลบ

## กล่องขั้นถัดไป

ปิดทุกเทิร์นด้วยกล่องนี้ (ถ้าแอปมี `wrap_up` ให้ใช้เป็นคำถามและปุ่มด้วย แต่ข้อความนี้ต้องอยู่ในคำตอบเสมอ)

กล่องมี 2 แบบ เลือกตามสิ่งที่ผู้ใช้ต้องทำ **กรอบ ``` ใช้กับสิ่งที่คัดลอกไปวางได้เท่านั้น** ห้ามใส่รายการตรวจ เงื่อนไข หรือคำอธิบายในกรอบ (ปุ่มคัดลอกของแอปจะหยิบทั้งกรอบ)

````text
▶ ต่อไป พิมพ์:
```

```
   หลังจากนั้น: <สิ่งที่ตามมา เช่น "พิมพ์ /kickstart เพื่อไปขั้น 6">
````

แบบ **ตอบ** (ผู้ใช้ต้องตัดสินหรือตอบ) ไม่มีกรอบ เขียนคำถามหนึ่งบรรทัดที่ตอบสั้นๆ ได้ (เช่น "อนุมัติ" หรือ "แก้ข้อ X") รายการที่ต้องตรวจเขียนไว้ในเนื้อตอบเหนือกล่อง ไม่ใช่ในกล่อง

```text
✅ ยังอยู่ขั้น <N>: <รออะไร>
▶ ต่อไป ตอบ: <คำถามหนึ่งบรรทัด>
   หลังจากนั้น: <สิ่งที่ผมทำต่อเมื่อได้คำตอบ และคำสั่งที่ผู้ใช้พิมพ์ต่อ>
```

- คำสั่งในกรอบต้อง **เติมค่าจริงครบ** (ชื่อฟีเจอร์ path เลข ticket) ห้ามมี `<...>` เหลือ
- คำสั่งที่เป็นสกิลต้องขึ้นต้นบรรทัดด้วย `/` และอยู่บรรทัดของตัวเอง บอกผู้ใช้ว่าห้ามพิมพ์ต่อท้ายประโยคอื่น (สกิลจะไม่ทำงาน)
- ถ้าขั้นถัดไป Claude ทำต่อได้เองโดยไม่ต้องรอใคร ให้ทำต่อในเทิร์นเดียวกัน ไม่ต้องหยุดถาม
- ถ้าควรเปิด session ใหม่ ให้บอกในกล่อง

## กติกา

- อนุมัติทุกจุดต้องมาจากผู้ใช้ในแชต ห้ามอนุมานว่า "น่าจะโอเค"
- ห้ามแก้ไฟล์ใน KIT จากสกิลนี้ ถ้าเจอว่าพรอมต์หรือแผนมีปัญหา ให้เสนอใน `KIT/ideas.md` ตามแบบฟอร์ม
- งานขนาดเล็ก (1–3 วัน): ขั้น 0 แบบย่อ → 1 → 3 แล้วบอกให้ใช้ `/tdd` ข้ามขั้น 2, 2.5, 4, 5
- ถ้ามีหลายฟีเจอร์ค้าง ให้ถามว่าจะทำฟีเจอร์ไหน
