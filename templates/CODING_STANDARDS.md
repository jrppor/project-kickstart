# มาตรฐานการเขียนโค้ด

## วิธีใช้เอกสารนี้

- **ธรรมเนียมของ repo และ ADR ชนะเอกสารนี้เสมอ** ถ้าขัดกัน ให้ทำตาม repo แล้วแก้ข้อในเอกสารนี้ให้ตรง เช่น ADR กำหนดให้ใช้ Result แทน exception
- ทุกข้อมีรหัส (เช่น `ERR-2`) ตอนรีวิวให้อ้างรหัส ข้อที่ขึ้นต้นด้วย **ข้อสังเกต** เป็นแนวทาง ไม่ใช่ข้อห้ามตายตัว
- ข้อที่มี `[tool]` ต่อท้าย ควรให้เครื่องมือบังคับ (lint, compiler, ด่านตรวจ) รีวิวไม่ต้องไล่ตรวจเอง
- **ตอนคัดลอกเข้า repo:** ส่วนกลางเก็บไว้เสมอ ส่วนหมวดตามส่วนประกอบ (SQL, API, FE, UI, APP, CLI, WORKER, LIB) ภาคผนวกโดเมน และภาษาที่ repo ไม่ใช้ให้ลบทิ้ง แล้วปรับข้อที่ ADR ตัดสินไว้ต่างออกไป
- คำว่า **ขอบระบบ** ในเอกสารนี้หมายถึงจุดที่ข้อมูลหรือคำสั่งเข้ามาจากภายนอก เช่น HTTP request · message ในคิว · argument ของ CLI · ไฟล์ · env · การกดบนหน้าจอ

## ส่วนกลาง (ใช้ทุกโปรเจกต์)

### ERR · การจัดการ error

- **ERR-1** ห้ามกลืน error ทุก catch หรือ `if err != nil` ต้องทำอย่างน้อยหนึ่งอย่าง: log พร้อม context · ส่งต่อ · จัดการจริง
- **ERR-2** จัดการหรือส่งต่อ อย่าทำทั้งสองอย่าง ห้าม log แล้วส่งต่อซ้ำทุกชั้นจนได้ log ซ้ำ ให้ log ครั้งเดียวที่ขอบระบบ
- **ERR-3** แยก error ที่คาดได้ (validation · ไม่พบ · ผิดกฎธุรกิจ · version ชน) ออกจาก error ที่ไม่คาดคิด ที่คาดได้ใช้กลไกตาม ADR (Result หรือ exception เฉพาะ) ที่ไม่คาดคิดปล่อยไปที่ handler กลาง
- **ERR-4** catch ให้แคบที่สุดเท่าที่จำเป็น ห้าม catch `Exception`/`Throwable` ทั้งหมด ยกเว้นที่ขอบระบบ
- **ERR-5** ข้อความ error ต้องบอกว่ากำลังทำอะไรอยู่ พร้อมค่าที่ช่วย debug แต่ห้ามมี secret หรือข้อมูลส่วนบุคคล
- **ERR-6** fail fast ตรวจ input หรือ state ที่ผิดตั้งแต่ต้นทาง อย่าปล่อยให้ไปพังที่อื่น
- **ERR-7** ห้ามส่งรายละเอียดภายใน (stack trace, SQL, path, ชื่อ class) ให้ผู้ใช้หรือผู้เรียกเห็น ไม่ว่าจะผ่าน response ของ API ข้อความบนหน้าจอ หรือ output ของ CLI

### NAME · การตั้งชื่อ

- **NAME-1** คำในโดเมนต้องตรงกับ `GLOSSARY.md` ทุกที่ที่ปรากฏ (โค้ด ที่เก็บข้อมูล API คำสั่ง ข้อความบนหน้าจอ) หนึ่งความหมายใช้หนึ่งคำ
- **NAME-2** ชื่อต้องบอกความหมาย ห้ามตัวย่อกำกวม (`tmp`, `data2`, `mgr`) ยกเว้นชื่อสั้นตามธรรมเนียมของภาษา (ดูภาคผนวกภาษา)
- **NAME-3** boolean ขึ้นต้นด้วย `is` / `has` / `can` / `should`
- **NAME-4** ตัวพิมพ์ตามธรรมเนียมของภาษา `[tool]`

### FUNC · โครงสร้างฟังก์ชัน

- **FUNC-1** ซ้อนไม่เกิน 3 ชั้น ใช้ early return
- **FUNC-2** ข้อสังเกต: ฟังก์ชันยาวเกินราว 40 บรรทัด หรือรับพารามิเตอร์เกิน 4 ตัว ให้พิจารณาแยก หรือรวมพารามิเตอร์เป็น object
- **FUNC-3** ห้ามใช้ boolean parameter ที่สลับพฤติกรรมเป็นสองโหมด ให้แยกเป็นสองฟังก์ชัน
- **FUNC-4** แยกกฎธุรกิจและการคำนวณ (pure) ออกจาก I/O เพื่อให้เทสต์ได้โดยไม่ต้องมี DB หรือ network
- **FUNC-5** ซ้ำ 2 ครั้งยังรับได้ ให้รวมเมื่อซ้ำครั้งที่ 3 ห้ามสร้าง abstraction เผื่ออนาคต

### TYPE · ความปลอดภัยของ type

- **TYPE-1** ห้ามใช้ `any` / `object` / `interface{}` ถ้าไม่จำเป็นจริง
- **TYPE-2** validate และแปลงเป็น type ของโดเมนที่ขอบระบบ ข้างในให้เชื่อ type ได้
- **TYPE-3** ค่าที่มีความหมายใช้ type เฉพาะ ไม่ใช้ primitive ลอยๆ: เงิน · รหัส (id) · สกุลเงิน · หน่วย · เปอร์เซ็นต์
- **TYPE-4** ค่าที่เป็น null ได้ต้องเห็นใน type (nullable reference types, `strictNullChecks`, pointer หรือค่า `ok`) `[tool]`

### COMMENT · comment

- **COMMENT-1** comment อธิบาย "ทำไม" (เหตุผล การตัดสินใจ ข้อควรระวัง) ไม่อธิบาย "ทำอะไร" ที่อ่านจากโค้ดได้อยู่แล้ว
- **COMMENT-2** ยกเว้น doc comment ของ API สาธารณะตามธรรมเนียมของภาษา
- **COMMENT-3** ห้ามทิ้งโค้ดที่ comment ไว้ และห้ามมี dead code
- **COMMENT-4** TODO ต้องอ้างถึง ticket

### SEC · ความปลอดภัย

- **SEC-1** ถ้ามีผู้ใช้หลายบทบาท ตรวจสิทธิ์ในฝั่งที่ผู้ใช้แก้ไม่ได้ (server, service) ทุกจุดที่รับคำสั่ง การซ่อนปุ่มบนหน้าจอหรือการตรวจในแอปฝั่ง client ไม่นับเป็นการตรวจ ต้องตรวจทั้งบทบาทและความเป็นเจ้าของข้อมูล (กัน IDOR)
- **SEC-2** วงเงินหรือขีดจำกัดตามบทบาท ตรวจในฝั่งที่ผู้ใช้แก้ไม่ได้เสมอ
- **SEC-3** input จากภายนอกทุกตัวต้องผ่าน validation (ชนิด ขนาด ช่วงค่า รูปแบบ) ก่อนใช้
- **SEC-4** ห้ามมี secret ในโค้ด repo log หรือไฟล์ที่แจกจ่ายให้ผู้ใช้ (แอป, แพ็กเกจ) ให้อ่านจาก env หรือ secret store และห้าม commit `.env`
- **SEC-5** ห้ามประกอบ SQL, คำสั่ง shell หรือ path จาก input โดยตรง
- **SEC-6** ไฟล์ที่รับจากภายนอก (อัปโหลด, import, ไฟล์ที่ผู้ใช้เปิด): จำกัดขนาด · ตรวจชนิดจากเนื้อไฟล์ ไม่ใช่จากนามสกุล · ห้ามใช้ชื่อหรือ path ที่ได้มาตรงๆ
- **SEC-7** ถ้ามีการยืนยันตัวตน: รหัสผ่าน hash ด้วย bcrypt หรือ argon2 · access token อายุสั้น · refresh token เพิกถอนได้

### LOG · log และข้อมูลส่วนบุคคล

- **LOG-1** ใช้ structured log ที่มี id สำหรับไล่ย้อน (request id, job id หรือ run id ตามรูปแบบโปรเจกต์)
- **LOG-2** ห้าม log secret, token, รหัสผ่าน, เลขบัตรประชาชน, เลขบัญชีหรือเลขบัตรเต็ม, ข้อมูลสุขภาพ ให้ปิดบังเป็นค่าเริ่มต้น
- **LOG-3** ข้อมูลอ่อนไหวแสดงแบบปิดบังเป็นค่าเริ่มต้นในทุกช่องทาง (หน้าจอ, response, output, รายงาน) การเปิดดูค่าเต็มต้องมีสิทธิ์และบันทึก audit
- **LOG-4** ใช้ระดับ log ให้ถูก `error` หมายถึงต้องมีคนมาดู ไม่ใช้กับเหตุการณ์ปกติ

### CONC · การแก้ข้อมูลพร้อมกันและการทำซ้ำ

- **CONC-1** ถ้าข้อมูลถูกแก้พร้อมกันได้ คำสั่งที่เปลี่ยนสถานะใช้ optimistic concurrency (version หรือ rowversion) ถ้าชนให้คืนเป็น error ที่คาดได้ (เช่น HTTP 409)
- **CONC-2** คำสั่งที่มีผลภายนอกหรือเกี่ยวกับเงินต้อง idempotent (idempotency key หรือ unique constraint) ส่งซ้ำแล้วต้องไม่เกิดผลซ้ำ
- **CONC-3** การส่งอีเมล ส่ง event หรือสั่งงานเบื้องหลังที่ผูกกับการเปลี่ยนข้อมูล ต้องบันทึกใน transaction เดียวกัน (outbox) หรือทำตามที่ ADR กำหนด
- **CONC-4** retry เฉพาะ error ชั่วคราว ต้องมี backoff และจำกัดจำนวนครั้ง

### TIME · เวลาและวันที่

- **TIME-1** เวลา (timestamp) เก็บเป็น UTC แล้วแปลงตอนแสดงผล
- **TIME-2** วันที่ทางธุรกิจ (วันเกิดเหตุ วันครบกำหนด วันทำการ วันซื้อขาย) เก็บเป็น date ที่ไม่มีเวลา และตีความตาม timezone ของธุรกิจ ซึ่งตั้งค่าไว้ที่เดียว
- **TIME-3** ห้ามเรียกนาฬิกาจริงในโค้ดโดเมน ให้ inject clock เข้ามา
- **TIME-4** ช่วงเวลาใช้แบบ half-open `[start, end)`

### TEST · คุณภาพเทสต์

- **TEST-1** ชื่อเทสต์บอกพฤติกรรม ไม่ใช่ชื่อเมธอด (`rejects_expired_token` ไม่ใช่ `testToken2`)
- **TEST-2** Arrange–Act–Assert หนึ่งพฤติกรรมต่อเทสต์
- **TEST-3** เทสต์อิสระจากกัน รันเดี่ยวหรือสลับลำดับได้
- **TEST-4** ผลต้องคงที่: ควบคุมเวลาและค่าสุ่ม ห้ามใช้ sleep รอ
- **TEST-5** unit test ห้ามมี I/O จริง ส่วน integration test ใช้ของจริงใน container ได้ (DB, queue) แต่ต้องแยกข้อมูลของแต่ละเทสต์
- **TEST-6** ตรวจผลที่สังเกตได้ ห้าม mock จนเทสต์แค่ทวนโค้ด refactor ที่พฤติกรรมเหมือนเดิมต้องไม่ทำให้เทสต์พัง
- **TEST-7** ครอบทั้ง happy path, edge case และ error case
- **TEST-8** แก้บั๊กต้องมีเทสต์ที่แดงก่อนแก้และเขียวหลังแก้
- **TEST-9** กฎการคำนวณ (เงิน วันที่ เกณฑ์) มีเทสต์แบบตารางที่ครอบค่าขอบ
- **TEST-10** โค้ดเทสต์ใช้มาตรฐานเดียวกับโค้ดจริง
- **TEST-11** ทรัพยากรของเทสต์ (ชื่อ DB, Redis db, พอร์ต, โฟลเดอร์ชั่วคราว) แยกจากของ dev และรับค่าจาก environment ได้ เพื่อให้หลาย worktree รันพร้อมกันโดยไม่ล้างข้อมูลของกันและกัน ตัวช่วยล้างข้อมูลต้องปฏิเสธเมื่อชี้ไปที่ของ dev

### DEP · dependency

- **DEP-1** เพิ่ม dependency ต้องมีเหตุผลเขียนใน commit และต้อง lock เวอร์ชัน
- **DEP-2** ห้ามใช้ package ที่เลิกดูแลแล้ว หรือมีช่องโหว่ที่รู้แล้วยังไม่แก้

### GEN · ทั่วไป

- **GEN-1** ทำตามธรรมเนียมของโค้ดรอบข้างก่อน
- **GEN-2** diff มีเฉพาะสิ่งที่งานต้องการ ห้ามมีการแก้ที่ไม่เกี่ยวข้องปนมา
- **GEN-3** เขียนให้คนอ่านง่าย ไม่ต้องเขียนให้ดูฉลาด ห้าม one-liner ที่อ่านยาก และห้าม ternary ซ้อน
- **GEN-4** การเปลี่ยนที่ทำให้ CLAUDE.md, ADR, README หรือเอกสารใน `docs/` ผิด ต้องแก้เอกสารนั้นใน commit หรือ ticket เดียวกัน ห้ามเลื่อนไปทำทีหลัง

## หมวดตามส่วนประกอบ (เก็บเฉพาะที่โปรเจกต์มี ดู `03-project-shapes.md` ของ project-kickstart)

### SQL · ฐานข้อมูล (ถ้ามีฐานข้อมูลเชิงสัมพันธ์)

- **SQL-1** table และ column ใช้ `snake_case` · primary key ชื่อ `id` · foreign key ชื่อ `<entity>_id` · index ชื่อ `idx_<table>_<columns>` (หรือตาม ADR และธรรมเนียมของ DB นั้น เช่น SQL Server นิยม PascalCase)
- **SQL-2** ห้าม `SELECT *` ในโค้ดของแอป
- **SQL-3** ใช้ parameterized query เสมอ แม้เป็น query ภายใน
- **SQL-4** constraint อยู่ใน DB (FK, unique, NOT NULL, CHECK) ไม่ใช่แค่ในโค้ด
- **SQL-5** WHERE ต้อง sargable ห้ามครอบ column ที่มี index ด้วยฟังก์ชันหรือการแปลงชนิด
- **SQL-6** ทุกการเปลี่ยน schema เป็น migration ห้ามแก้ migration ที่ merge แล้ว ให้สร้างไฟล์ใหม่
- **SQL-7** ห้าม N+1 query และ list ต้องแบ่งหน้าพร้อมกำหนดจำนวนสูงสุด
- **SQL-8** transaction ครอบหนึ่ง use case และสั้นที่สุด ห้ามเรียก network ภายนอกระหว่าง transaction

### API · สัญญา API (ถ้าเปิด HTTP/gRPC ให้ระบบอื่นหรือแอปของเราเรียก)

- **API-1** error ใช้รูปแบบเดียวทั้งระบบ (เช่น ProblemDetails) และมี code ที่เครื่องอ่านได้
- **API-2** สัญญา API (OpenAPI หรือ proto) อัปเดตพร้อมโค้ดใน commit เดียวกัน
- **API-3** การเปลี่ยนแบบ breaking ต้องมี version ใหม่ หรือมีช่วงที่รองรับทั้งแบบเก่าและใหม่ (สำคัญมากเมื่อมีแอป mobile ที่ผู้ใช้ไม่อัปเดต)
- **API-4** filter และ sort รับเฉพาะ field ที่อยู่ใน allowlist
- **API-5** มี health check ที่บอกได้ว่าพร้อมรับงานจริง (เช่นต่อ DB ได้) แยกจากแค่ process ยังทำงานอยู่
- **API-6** ไฟล์สัญญาที่ commit ไว้มีเทสต์เทียบกับสัญญาที่โค้ดสร้างจริง และฝั่งที่เรียกใช้ generate type จากไฟล์นั้นพร้อมเทสต์ว่าตรงกัน แก้สัญญาโดยไม่ตั้งใจแล้วด่านต้องแดง

### FE · หน้าเว็บ (ถ้ามีหน้าเว็บ)

- **FE-1** ห้ามมี secret ในโค้ดฝั่ง client รวมถึงตัวแปร `NEXT_PUBLIC_*` และ environment ของ Angular
- **FE-2** แยกให้ชัดว่าโค้ดไหนรันฝั่ง server และฝั่ง client ไม่ส่งข้อมูลอ่อนไหวลง client ถ้าหน้าจอไม่ได้ใช้
- **FE-3** ฟอร์มใช้ schema ชุดเดียวกับที่ตรวจตอนส่ง และ server ต้องตรวจซ้ำเสมอ
- **FE-4** ทุกหน้าที่โหลดข้อมูลต้องมีสถานะ loading, error และ empty
- **FE-5** accessibility: input มี label · ใช้คีย์บอร์ดได้ · ไม่สื่อความหมายด้วยสีอย่างเดียว
- **FE-6** จัดรูปแบบตัวเลข เงิน และวันที่ผ่าน helper ชุดเดียว ห้ามจัดเองกระจายหลายที่

### UI · หน้าตาและการออกแบบ (ถ้ามีหน้าจอ ใช้คู่กับ FE หรือ APP)

- **UI-1** สี ขนาดตัวอักษร ระยะห่าง มุมโค้ง และเงา ใช้ design token หรือ theme เท่านั้น ห้าม hardcode ค่าใน component
- **UI-2** ใช้ component จาก library หรือ component กลางของโปรเจกต์ก่อนสร้างใหม่ ถ้ารูปแบบเดียวกันซ้ำครั้งที่ 2 ให้ยกเป็น component กลาง
- **UI-3** หน้าจอต้องตรงกับ prototype หรือ mockup ที่ยอมรับแล้ว ถ้าต้องต่างออกไป ให้บอกเหตุผลและแก้ mockup ให้ตรง
- **UI-4** ใช้งานได้ทุกขนาดจอหรือ breakpoint ที่ ADR กำหนด และห้ามมี scroll แนวนอนบนจอมือถือ
- **UI-5** ข้อความภาษาไทยต้องไม่ถูกตัด: ห้ามกำหนดความสูงตายตัวจนสระบนสระล่างหาย และข้อความยาวต้องขึ้นบรรทัดใหม่หรือย่อพร้อมแสดงเต็มได้
- **UI-6** สีของข้อความและพื้นหลังมี contrast ผ่าน WCAG AA และสถานะสำคัญ (ผิดพลาด เตือน สำเร็จ) ไม่สื่อด้วยสีอย่างเดียว
- **UI-7** mobile และ desktop ทำตามแนวทางของแพลตฟอร์ม (Material, Human Interface Guidelines, Fluent) ยกเว้นที่ ADR ด้านการออกแบบตัดสินไว้ต่างออกไป
- **UI-8** หน้าที่เพิ่มหรือเปลี่ยน ต้องตรวจด้วยภาพหน้าจอจริงอย่างน้อยขนาดจอมือถือและ desktop ก่อน merge

### APP · แอป mobile และ desktop (ถ้ามี)

- **APP-1** ห้ามฝัง secret ในแอป ทุกอย่างที่อยู่ในไฟล์แอปถือว่าคนอื่นแกะอ่านได้ การตรวจสิทธิ์ทั้งหมดอยู่ฝั่ง server
- **APP-2** token และข้อมูลลับเก็บใน secure storage ของระบบ (Keychain, Keystore, Credential Manager/DPAPI) ห้ามเก็บเป็นไฟล์หรือ preferences ธรรมดา
- **APP-3** งานที่ใช้เวลา (network, ไฟล์, DB) ห้ามทำบน UI thread
- **APP-4** ทุกหน้าจอมีสถานะ loading, error, empty และ **offline** ตามที่ ADR ตัดสินว่าต้องทำงาน offline ได้แค่ไหน
- **APP-5** ขอ permission เฉพาะตอนจะใช้ และแอปต้องทำงานต่อได้อย่างเหมาะสมเมื่อผู้ใช้ปฏิเสธ
- **APP-6** แอปเวอร์ชันเก่าที่ผู้ใช้ยังไม่อัปเดตต้องไม่พัง มีวิธีบังคับอัปเดตเมื่อจำเป็น และข้อมูลที่เก็บในเครื่องต้อง migrate ได้
- **APP-7** ข้อความและรูปแบบตัวเลข วันที่ เงิน ผ่านระบบ localization ชุดเดียว
- **APP-8** accessibility: ขนาดตัวอักษรตามที่ระบบตั้ง · screen reader อ่านปุ่มได้ · เป้าแตะใหญ่พอ

### CLI · โปรแกรม console (ถ้ามี)

- **CLI-1** exit code คือสัญญา: `0` สำเร็จ ค่าอื่นล้มเหลว และความหมายของแต่ละค่าเขียนไว้ใน README
- **CLI-2** ผลลัพธ์ออก stdout ส่วนข้อความ error, log และ progress ออก stderr เพื่อให้ต่อ pipe ได้
- **CLI-3** มี `--help` ที่บอกทุก argument และตัวอย่าง และ argument ที่ผิดต้องบอกวิธีแก้
- **CLI-4** ห้ามถามแบบ interactive เมื่อไม่ได้รันใน terminal (เช่นใน CI หรือ pipe) ต้องมี flag ให้ใส่ค่าแทนได้
- **CLI-5** ลำดับความสำคัญของ config ชัดเจน: argument > env > ไฟล์ config > ค่าเริ่มต้น
- **CLI-6** ถ้ามีโหมดให้เครื่องอ่าน (เช่น `--json`) รูปแบบ output ถือเป็นสัญญา เปลี่ยนต้องระวังเหมือน API
- **CLI-7** คำสั่งที่ลบหรือเปลี่ยนข้อมูลมี `--dry-run` หรือขอยืนยัน และหยุดอย่างเรียบร้อยเมื่อกด Ctrl+C
- **CLI-8** output สำคัญมี golden test ที่ commit ไว้

### WORKER · background service และงานตามเวลา (ถ้ามี)

- **WORKER-1** ถือว่างานอาจถูกส่งซ้ำได้ (at-least-once) handler ทุกตัวต้อง idempotent
- **WORKER-2** งานที่ล้มซ้ำเกินกำหนดต้องไปที่ dead-letter พร้อมเหตุผล ห้ามวนไม่จบ หรือทิ้งไปเงียบๆ
- **WORKER-3** หยุดอย่างเรียบร้อยเมื่อได้รับสัญญาณหยุด: ไม่รับงานใหม่ ทำงานที่ค้างให้จบหรือคืนเข้าคิว
- **WORKER-4** มี health check หรือ heartbeat ให้รู้ว่ายังทำงานอยู่ และมี metric พื้นฐาน (จำนวนงานค้าง เวลาที่ใช้ อัตราล้ม)
- **WORKER-5** งานตามเวลาต้องกันการรันซ้อนเมื่อมีหลาย instance (lock หรือ leader election) และกำหนดว่ารอบที่พลาดไปต้องรันชดเชยหรือไม่
- **WORKER-6** ทุกงานมี timeout และใช้ทรัพยากรแบบจำกัด (จำนวนงานพร้อมกัน, ขนาด batch)
- **WORKER-7** log ของแต่ละงานมี id ของงานนั้น เพื่อไล่ย้อนได้

### LIB · library และ SDK (ถ้ามี)

- **LIB-1** public API เล็กที่สุดเท่าที่จำเป็น สิ่งที่ไม่ตั้งใจให้คนอื่นใช้ต้องไม่ export
- **LIB-2** ใช้ semantic versioning การเปลี่ยนแบบ breaking ต้องขึ้นเลข major และเขียนไว้ใน CHANGELOG
- **LIB-3** ห้ามมี global state ห้ามเขียนลง stdout เอง และห้ามจบ process ให้ผู้เรียกเป็นคนตัดสินใจ log และ error
- **LIB-4** dependency ให้น้อยที่สุด และไม่บังคับเวอร์ชันแคบเกินจำเป็น
- **LIB-5** ทุก public API มี doc comment และตัวอย่างการใช้ที่รันอยู่ในเทสต์
- **LIB-6** ตรวจว่า public API ไม่เปลี่ยนโดยไม่ตั้งใจ (เช่นเครื่องมือ API diff หรือเทสต์ที่ล็อกรายการ API)

## ภาคผนวก ก · โดเมน (เก็บเฉพาะที่ repo ใช้)

### ก1 · MONEY · เงินและบัญชี (ทุกระบบที่มีเงิน: ประกัน ธนาคาร ชำระเงิน หุ้น e-commerce)

- **MONEY-1** ห้ามใช้ `float` / `double` / `number` ของ JS กับเงิน ให้ใช้ decimal หรือ `numeric(p,s)` หรือเก็บเป็นจำนวนเต็มของหน่วยย่อย (สตางค์) API ส่งเงินเป็น string
- **MONEY-2** จำนวนเงินมาคู่กับสกุลเงินเสมอ (Money type) และห้ามบวกลบต่างสกุลเงินกันโดยตรง
- **MONEY-3** วิธีปัดเศษ (half-up หรือ banker's) และจุดที่ปัด กำหนดไว้ที่เดียว ปัดครั้งเดียวตอนขั้นสุดท้าย ห้ามปัดระหว่างทาง
- **MONEY-4** การแบ่งเงิน (ผ่อน แบ่งจ่าย แบ่งสัดส่วน) ผลรวมหลังแบ่งต้องเท่ายอดเดิม และต้องมีวิธีจัดการเศษที่เหลือ
- **MONEY-5** ยอดคงเหลือต้องคำนวณได้จากรายการ (ledger) ห้ามแก้ยอดตรงๆ รายการที่บันทึกแล้วห้ามแก้หรือลบ ให้แก้ด้วยรายการกลับ (reversal)
- **MONEY-6** การบันทึกบัญชีแบบ double-entry ทุก transaction เดบิตต้องเท่าเครดิต ตรวจด้วย constraint หรือเทสต์
- **MONEY-7** การเปลี่ยนยอดเงินต้อง atomic และกันยอดติดลบหรือการใช้ยอดซ้ำ (lock แถว หรือ conditional update)
- **MONEY-8** อัตราที่ใช้คำนวณ (แลกเปลี่ยน ดอกเบี้ย เบี้ย ค่าธรรมเนียม) บันทึกค่าที่ใช้จริงพร้อมเวลาไว้กับรายการ

### ก2 · BANK · ธนาคารและการชำระเงิน

- **BANK-1** เลขบัญชีและเลขบัตรปิดบังเสมอ ยกเว้นจุดที่จำเป็นจริง ถ้าไม่จำเป็นอย่าเก็บเลขบัตรเอง ให้ใช้ token ของผู้ให้บริการ
- **BANK-2** คำสั่งเงินออกต้อง idempotent และมีสถานะชัด (pending · succeeded · failed · unknown) ถ้าปลายทาง timeout ให้ถือเป็น unknown ไม่ใช่ failed และต้องสอบยันก่อนลองใหม่
- **BANK-3** มี reconciliation กับปลายทาง (statement หรือไฟล์ตอบกลับ) และรายการที่ไม่ตรงต้องมีคนตรวจ
- **BANK-4** วันทำการ วันหยุด และ cut-off time มาจากปฏิทินที่ตั้งค่าได้ ห้าม hardcode
- **BANK-5** การกระทำที่มีความเสี่ยงสูงใช้ maker-checker (คนสร้างกับคนอนุมัติต้องเป็นคนละคน) และตรวจฝั่ง server

### ก3 · SECURITIES · หลักทรัพย์และการซื้อขาย (ไม่ใช่ระบบสต็อกสินค้า)

- **SECURITIES-1** ราคาและจำนวนใช้ decimal และตรวจให้ตรง tick size กับ lot size ของหลักทรัพย์ก่อนส่งคำสั่ง
- **SECURITIES-2** คำสั่งซื้อขายมี client order id ที่ไม่ซ้ำ (idempotent) และ state machine ชัด (new · partially filled · filled · cancelled · rejected)
- **SECURITIES-3** ข้อมูลตลาดเก็บเวลาจากแหล่ง (exchange timestamp) แยกจากเวลาที่ได้รับ และตรวจข้อมูลที่เก่าเกินไป (stale)
- **SECURITIES-4** วันและชั่วโมงทำการของตลาดรวมถึง timezone ของตลาด มาจากปฏิทินที่ตั้งค่าได้ ห้าม hardcode
- **SECURITIES-5** วิธีคิดต้นทุนและกำไร (FIFO หรือถัวเฉลี่ย) กำหนดไว้ที่เดียว ถ้ารองรับ corporate action ต้องมีเทสต์ครอบ
- **SECURITIES-6** position ต้องคำนวณซ้ำจากรายการ trade ได้เสมอ

### ก4 · AUDIT · ระบบที่ต้องตรวจสอบย้อนหลังได้ (ประกัน ธนาคาร หุ้น ราชการ การแพทย์)

- **AUDIT-1** การเปลี่ยนสถานะ การอนุมัติ และการเปิดดูข้อมูลอ่อนไหว ต้องบันทึก audit: ใคร · ทำอะไร · เมื่อไร · ค่าเดิม · ค่าใหม่ · เหตุผล
- **AUDIT-2** audit log เขียนเพิ่มได้อย่างเดียว แอปแก้หรือลบไม่ได้
- **AUDIT-3** สถานะใช้ state machine ที่ประกาศชัด การเปลี่ยนสถานะที่ไม่อนุญาตต้องถูกปฏิเสธ และมีเทสต์ครอบทุกเส้นทาง
- **AUDIT-4** ข้อมูลอ้างอิงที่ใช้ตัดสินใจ (อัตรา เงื่อนไขสัญญา วงเงิน) ต้องเรียกดูค่า ณ เวลานั้นย้อนหลังได้ (versioned หรือ snapshot)
- **AUDIT-5** กำหนดระยะเวลาเก็บและการลบข้อมูลตามกฎหมาย (เช่น PDPA) แยกตามประเภทข้อมูล

## ภาคผนวก ข · ภาษา (เก็บเฉพาะที่ repo ใช้)

### Go

- wrap error ด้วย `fmt.Errorf("...: %w", err)` ตรวจด้วย `errors.Is` / `errors.As` และห้ามทิ้ง error ด้วย `_`
- ห้าม `panic` ในเส้นทางปกติ
- `context.Context` เป็นพารามิเตอร์แรกและส่งต่อทุกชั้น
- goroutine ทุกตัวต้องมีทางจบ (context หรือ channel ปิด)
- ห้ามชื่อซ้ำกับชื่อ package (`claims.Service` ไม่ใช่ `claims.ClaimService`) ชื่อสั้นที่อนุญาต: `ctx`, `err`, `ok`, `i`, `r`, `w`, ชื่อ receiver ตัวเดียว
- `gofmt` + `go vet` `[tool]`

### C# / .NET

- เปิด nullable reference types และให้ warning เป็น error `[tool]`
- async ตลอดสาย ห้าม `.Result` / `.Wait()` และส่ง `CancellationToken` ต่อทุกชั้น
- เงินใช้ `decimal` · วันที่ทางธุรกิจใช้ `DateOnly` · เวลาใช้ `DateTimeOffset`
- resource ที่เป็น `IDisposable` ใช้ `using`

### Java / Spring

- `BigDecimal` สร้างจาก string (`new BigDecimal("0.10")`) และเทียบค่าด้วย `compareTo` ห้ามใช้ `equals` เพราะ `equals` เทียบ scale ด้วย
- ใช้ `java.time` เท่านั้น ห้ามใช้ `Date` / `Calendar`
- `@Transactional` อยู่ที่ service ไม่ใช่ controller และใช้ constructor injection
- ห้ามใช้ `Optional` เป็น field หรือพารามิเตอร์

### TypeScript / React / Next.js

- `strict` เปิด · ห้าม `any` และ `!` (non-null assertion) `[tool]`
- validate ข้อมูลจากภายนอกด้วย schema (เช่น zod) ที่ขอบระบบ
- server action และ route handler ต้องตรวจสิทธิ์เอง อย่าพึ่งการตรวจของ middleware อย่างเดียว
- `key` ใน list ต้องคงที่ (ห้ามใช้ index ถ้าลำดับเปลี่ยนได้) · `useEffect` ต้องมี dependency ครบและ cleanup `[tool]`
- ถ้าใช้ไลบรารีจัดการข้อมูลอยู่แล้ว (เช่น TanStack Query) อย่า fetch เองใน `useEffect`

### Angular

- ใช้ `OnPush` เมื่อทำได้ และ subscription ต้องปิดเอง (`async` pipe หรือ `takeUntilDestroyed`)
- ใช้ typed forms และห้าม `any`
